# Отзывы с Яндекс.Карт

Вставляешь ссылку на организацию в Яндекс.Картах, приложение забирает её рейтинг, количество оценок, количество отзывов и сами отзывы, и показывает всё это с разбивкой по 50 штук на страницу.

Бэкенд на Laravel 13 (API + Sanctum), фронтенд на Vue 3 + TypeScript, база PostgreSQL, всё поднимается в Docker.

Демо: http://31.130.135.141:8090 (логин и пароль в письме). Стенд временный и поднят по HTTP, поэтому пароль там одноразовый: домен с сертификатом в списке «что сделал бы».

## Что внутри

- Вход. Регистрации нет, один пользователь создаётся при первом запуске.
- Настройки. Поле для ссылки. Подходит почти любая ссылка на организацию: из адресной строки, с регионом в адресе, с `?oid=`, короткая из кнопки «Поделиться». Если ссылка не на организацию, форма так и скажет. После сохранения загрузка отзывов сразу уходит в фон.
- Страница организации. Рейтинг, оценки и отзывы отдельными числами, сами отзывы (автор, дата, текст, оценка, ответ организации), страницы по 50. Пока идёт загрузка, видно прогресс, а отзывы появляются по мере скачивания. Можно нажать «Обновить данные» и посмотреть, что изменилось с прошлого раза.

## Как запустить у себя

Нужен только Docker.

```bash
cp .env.example .env
docker compose up -d --build
```

Открыть http://localhost:8095, войти `demo@example.com` / `demo12345`.

Поднимается пять контейнеров:
- `app`: PHP, при старте сам накатывает миграции и создаёт пользователя;
- `queue`: воркер, который парсит;
- `scheduler`: планировщик;
- `web`: nginx;
- `postgres`: база.

Ключ приложения генерировать не нужно, он создастся сам.

### Тесты

```bash
# бэкенд, 119 тестов
docker build --target dev -t yandex-reviews-dev .
docker run --rm -v "$PWD:/var/www/html" yandex-reviews-dev sh -c "composer install && php artisan test"

# фронтенд, 35 тестов
npm ci && npm run typecheck && npm test
```

Быстро проверить, что парсер понимает живой Яндекс (в базу ничего не пишет):

```bash
docker compose exec -u www-data app php artisan yandex:check
docker compose exec -u www-data app php artisan yandex:check "https://yandex.ru/maps/org/..."
```

`-u www-data` не для красоты: от root команда может первой за сутки создать файл лога, и тогда воркер с планировщиком в него уже не запишут.

## Как я парсю Яндекс

Браузер не использую. Вместо этого делаю то же, что делает сам сайт Яндекс.Карт.

1. Открываю страницу организации `yandex.ru/maps/org/{id}/reviews/`.

Разметку не разбираю. Карты рисуются из большого JSON, который лежит прямо в странице, в `<script class="state-view">`. Из него беру:
- название и адрес;
- `ratingData` с точными рейтингом, числом оценок и числом отзывов;
- токен и id сессии, без них Яндекс не отдаст отзывы.

2. Забираю отзывы через внутренний запрос карт `fetchReviews`, тот самый, которым сайт подгружает отзывы при прокрутке. По 50 штук на страницу, от новых к старым.

Пришлось покопаться в JS-коде карт:
- Подпись. У запроса есть параметр `s`. Это хэш от остальных параметров, без него Яндекс отвечает ошибкой. Алгоритм нашёл в их коде и повторил в `RequestSigner`, это 20 строк. Для теста эталон посчитан их же функцией.
- Устаревший токен. Если токен протух, Яндекс присылает новый, и запрос повторяется с ним. Сайт делает так же. Новый токен запоминается на всю загрузку: иначе каждая следующая страница снова получала бы отказ, и вместо 13 запросов выходило бы 25.
- Потолок в 600. Больше 12 страниц Яндекс не отдаёт никому, на 13-й отвечает ошибкой. Поэтому у организации с 5 000 отзывов получится 600 последних. Интерфейс это честно пишет.

Куки, User-Agent и прокси на всё время загрузки одной организации не меняются, иначе Яндекс не примет токен.

Где что лежит:
- `app/Services/YandexMaps`: всё про Яндекс, разбор ссылки, запросы, разбор ответов;
- `app/Services/Sync`: сохранение в базу;
- `app/Jobs/SyncOrganization`: фоновая задача.

Контроллеры про Яндекс ничего не знают.

## Почему отзывы грузятся в базу, а не с Яндекса при каждом открытии

Загружаю отзывы один раз в фоне, складываю в свою базу, а страницы по 50 штук отдаю уже из базы.

Если ходить в Яндекс за каждой страницей:
- долго: полная загрузка занимает 13 запросов с паузами, около 30 секунд (25, если Яндекс отверг токен со страницы);
- бан: каждый человек, пролиставший 12 страниц, делает 12 запросов к Яндексу, с таким трафиком быстро заблокируют;
- Яндекс недоступен: если он лёг или показал капчу, человек не увидит вообще ничего;
- нет истории: без своей базы не видно, что изменилось и какие отзывы удалили.

Чтобы не ждать полминуты при первом подключении, отзывы показываются по мере загрузки: первые 50 появляются через пару секунд, остальные подтягиваются, пока их листаешь. Номер страницы хранится в адресе (`?page=3`), страница при переключении не перезагружается.

## Ответы на дополнительные вопросы

### 1. Как парсер поймёт, что Яндекс что-то поменял

Главное правило: если ответ не похож на ожидаемый, это ошибка «источник изменился», а не пустой список.

Что проверяю:
- в странице есть JSON с данными, в нём есть токен и карточка организации;
- у рейтинга правильные поля. Блока с рейтингом может не быть совсем: это либо новая организация без оценок, либо переименованное поле, поэтому его отсутствие сверяется с числом отзывов из API. Нет блока, а отзывов сотни — ошибка. Нули поверх прежних цифр не пишутся ни при каком раскладе;
- в ответе с отзывами есть список и счётчики, у каждого отзыва есть id, оценка от 0 до 5, текст и дата в формате ISO 8601. Формат даты проверяется до разбора: `Carbon` молча превращает пустую строку в «сейчас»;
- ответ организации и ссылка на аватар разбираются так же строго, как остальные поля. А если на странице разом исчезли все ответы, которые были в базе, страница откатывается с ошибкой «источник изменился»: скорее переименовали поле, чем организация за ночь стёрла сотню ответов;
- нет странного: пустая страница посреди списка, ни у одного автора нет имени, на карточке отзывы есть, а в ответе ноль, скачано заметно меньше, чем обещано;
- «организации нет» отличается от «мы разучились читать выдачу»: у несуществующего id Яндекс отдаёт панель с пустым списком, а вот панель без списка или список, в котором нет ни одной карточки организации, считаются сменой формата;
- если Яндекс отвечает «Bad Request», значит, изменился сам запрос (так он отвечает на неверную подпись, проверял).

Что происходит, если сломалось:
- загрузка получает статус «источник изменился» и не повторяется, повтор не поможет;
- в лог пишется ошибка уровня `critical` с подробностями, что именно не сошлось. Капча, таймаут и «организации нет» под `critical` не попадают: там нужен не программист, а ожидание;
- пользователь видит понятное сообщение, а данные с прошлой удачной загрузки остаются на месте. Название и цифры карточки сохраняются сразу, как только она разобрана, поэтому даже сорвавшаяся посреди страниц загрузка не оставляет пустую страницу.

Раз в три часа работает проверка `php artisan yandex:check`. Она парсит эталонную организацию и падает, если что-то не так. Заодно проверяет, что Яндекс по-прежнему отдаёт ровно 12 страниц: если потолок опустят или поднимут, об этом будет сигнал. Капча и обрыв связи в этой проверке пишутся обычной ошибкой, а не `critical`, иначе на каждый чих прилетал бы ложный сигнал «парсер сломан».

Потолок ловится и при обычной загрузке: если Яндекс перестал отдавать страницу, которую сам же обещал, а все предыдущие пришли полными, это не разовый сбой. Такая загрузка сразу падает с «источник изменился», а не выжигает пять попыток по 12 запросов.

Сейчас всё это живёт в логе: отправку `critical` в Telegram или Sentry я не делал, она в списке «что сделал бы».

Какие бывают ошибки:

| Что случилось | Повторяем? |
|---|---|
| Яндекс изменил формат | нет, нужен человек |
| Организации нет | нет |
| Капча или блокировка | да, после паузы; ожидание паузы не тратит попыток |
| Сеть, таймаут, ошибка на стороне Яндекса | да: сначала эту же страницу, потом всю загрузку через 30 секунд, 2, 10 и 30 минут |
| Ссылка не на организацию | нет, ошибка в форме |

### 2. Почему не headless-браузер

| | Внутренние запросы (выбрал) | Headless-браузер |
|---|---|---|
| Скорость | 600 отзывов за ~30 секунд, и это с паузами | минуты на одну организацию: загрузить сайт, прокрутить, дождаться |
| Ресурсы | обычный PHP, десятки мегабайт | Chrome на 300-500 МБ на вкладку, под 50 филиалов нужен отдельный сервер |
| Данные | готовый JSON с точными цифрами и id отзывов | текст со страницы, цифры и id ещё надо выковыривать |
| Что ломается | формат JSON, подпись или токен | вёрстка, а у Яндекса классы генерируются и меняются часто |
| Видно ли поломку | да, проверка по каждому полю | плохо: «не нашёл элемент» может значить что угодно |
| Защита от ботов | запросы надо делать похожими на запросы сайта | похож на живого человека, капчу проще пройти |

Риски и что с ними делать:
- Поменяют подпись или токены. Проверка сразу это заметит, чинится правкой одного небольшого класса.
- Сильно закрутят защиту от ботов. Тогда подключу браузер, но только для входа на страницу и получения кук. Дальше тот же код разбора, переписывать ничего не придётся.

### 3. 50 филиалов и фоновая загрузка

Парсинг никогда не идёт внутри запроса пользователя. Сохранил ссылку, задача ушла в очередь, ответ пришёл сразу.

- Прогресс. После каждой скачанной страницы задача записывает, сколько страниц пройдено и сколько отзывов получено. Фронт раз в 2 секунды спрашивает статус и рисует полоску.
- Повторы. До 5 попыток с растущей паузой. Если Яндекс разово не отдал страницу, она перезапрашивается сразу, без повторного прохода с начала. Ожидание общей паузы после капчи считается отдельно и попыток не тратит: иначе бан на полтора часа отправил бы в «ошибку» всю ночную пачку, хотя запросов за это время не было ни одного.
- Повтор идёт с первой страницы, а не с той, где сорвалось. Так выходит немного лишних запросов, но выдача упорядочена по времени и сдвигается при каждом новом отзыве: начав с середины, легко пропустить отзыв и потом принять живой за удалённый. Сохранение идемпотентно, так что лишний проход просто перезапишет то же самое.
- Без двойных загрузок. Если по организации уже идёт загрузка, повторное нажатие «Обновить» не запустит вторую.
- Если воркер умер. Отдельная команда раз в пять минут закрывает загрузки, которые давно не подают признаков жизни, и кнопка «Обновить» снова работает. Порог считается от таймаута задачи и паузы после бана, чтобы живую загрузку не объявить зависшей.
- Все 50 филиалов раз в сутки ставятся в очередь командой `organizations:sync-all`. Запросы к Яндексу идут с общей паузой для всех воркеров, поэтому хватает одного-двух. 50 × 13 запросов по ~2 секунды выходит минут 25 на всю сеть, для ночного обновления нормально.

### 4. Как не получить бан

Сделано:
- Пауза между запросами. Общая для всех воркеров, плюс случайная добавка, чтобы не стучаться с машинной ровностью.
- Пауза после бана. Поймали капчу или отказ, и запросы останавливаются на 15 минут, задачи ждут её конца. Пауза своя у каждого выхода в интернет: забанили один прокси, остальные продолжают работать. Долбить уже подозрительный адрес хуже всего.
- Ведём себя как браузер. Сначала открываем страницу, берём куки и токен, потом запрашиваем отзывы с этими куками и правильным `Referer`.
- Выбор User-Agent и прокси. Берутся случайно на каждую загрузку организации, а не на каждый запрос: смена «браузера» посреди сессии выглядит ещё подозрительнее. Список User-Agent пока короткий и лежит в конфиге.
- Меньше запросов. Люди читают отзывы из нашей базы и в Яндекс лишний раз не ходят.

Что добавил бы на большом объёме:
- Хорошие прокси (резидентные или мобильные) и карантин по здоровью: прокси, который ловит капчу чаще других, должен выбираться реже, а не наравне со всеми.
- Обновлять только новое. Отзывы идут от новых к старым, поэтому при плановом обновлении можно остановиться, как только пошли уже известные. Обычно выйдет 1-2 запроса вместо 12.
- Размазать плановое обновление по суткам, а не ставить всю сеть филиалов в очередь разом.
- Если всё равно забанили, подключить сервис разгадывания капчи или браузер для получения кук.

### 5. Повторная загрузка и история изменений

Таблицы:

```
organizations           организации; одна и та же ссылка второй раз не создаёт дубль
sync_runs               каждая загрузка: статус, прогресс, итоги, текст ошибки
organization_snapshots  снимок рейтинга и счётчиков после каждой удачной загрузки
reviews                 отзывы; уникальны по id отзыва в Яндексе
review_revisions        история по отзыву: изменён, удалён, вернулся (что было и что стало)
```

Как это работает:
- Дубли. Отзыв узнаётся по его id в Яндексе. При повторной загрузке он обновляется, а не создаётся заново. Проверено вживую: повторная загрузка 600 отзывов не добавила ни одной записи.
- Изменения отзыва. Если автор поправил текст или оценку, или организация ответила, в историю пишется, что было и что стало.
- Удалённые отзывы. Не стираются, а помечаются. Есть тонкость: если у организации больше 600 отзывов, старый отзыв «пропадает» из выдачи просто потому, что его вытеснили новые, это не удаление. Поэтому удалённым считается только отзыв, который должен был попасть в выдачу, но не попал. А если за время загрузки число отзывов поменялось, список мог сдвинуться, и в этот раз удалённые не помечаются вовсе, чтобы случайно не спрятать живые.
- Склейка карточек. Яндекс объединяет дубли и может отдать карточку под новым id. Тогда организация переезжает на новый id, если он ещё не занят другой подключённой, а удалённые в этот раз не помечаются: отзывы могли приехать из второй карточки. Со следующей загрузки всё работает как обычно.
- Изменения карточки. Что было и что стало по рейтингу и счётчикам, видно по разнице между соседними снимками. На странице организации есть блок «История изменений».

## API

Всё, кроме входа, требует авторизации. Чужая организация отвечает «не найдено».

| Запрос | Что делает |
|---|---|
| `GET /sanctum/csrf-cookie` | получить куку перед входом |
| `POST /api/login` | вход, не больше 5 попыток в минуту |
| `POST /api/logout` | выход |
| `GET /api/user` | текущий пользователь |
| `GET /api/organizations` | список организаций со статусом загрузки |
| `POST /api/organizations` | добавить по ссылке и запустить загрузку |
| `GET /api/organizations/{id}` | организация, цифры и прогресс |
| `DELETE /api/organizations/{id}` | удалить вместе с отзывами |
| `POST /api/organizations/{id}/sync` | обновить данные |
| `GET /api/organizations/{id}/reviews?page=N` | 50 отзывов, новые сверху |
